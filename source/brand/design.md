# Design guide

How we look, everywhere: the website, the decks, any image we produce. The AI reads this plus `tokens.css` before any visual decision. The setup skill personalizes it; after that it grows one rule at a time.

## Philosophy

Institutional but alive: a hospital-and-engineering research chair, not a startup. Confident, restrained, generous whitespace, one big scrollable home page. Inspired by owkin.com and whitelabgx.com — mostly light, clinical-clean sections, punctuated by a couple of full-bleed dark-blue blocks for emphasis rather than color everywhere. Every visual decision should be defensible against this paragraph.

## Tokens

`tokens.css` is the only place where colors, fonts, and the spacing scale are defined. Nothing in `site/` or in a deck hardcodes a hex value, a font name, or a magic pixel number. Adding a design idea that needs a new value means adding the token first, with a name that says what it's for.

- **Color**: the BOPA logo's four blues (`--bopa-blue-1..4`) are the source. `--color-accent` is the darkest (`--bopa-blue-1`, best contrast on white); `--color-dark` is a deeper navy used only for full-bleed emphasis sections (hero, one spotlight section per page — not every other section). Neutrals are cool-toned to sit with the blues: a light blue-gray `--color-bg`, deep navy `--color-ink` instead of pure black.
- **The home's order and chromatic rhythm have both been revised twice in one week (2026-08-27, "V2" global restructuring → "V4.1" restructuring) - treat either as provisional, always verify current order/backgrounds live rather than trusting the last-written note.** Current order/tones (updated 2026-08-28, last touched when Nous contacter flipped to navy): Mission (navy) → Les innovations BOPA (its own established pale/near-white, left alone) → Notre Vision (navy) → Qui sommes-nous: 01 Chaire d'excellence (pale `--color-bg-tint`) → 02 Un écosystème unique dédié à l'innovation (light but **visibly more saturated blue** than 01, see the dedicated bullet below - no longer the dark navy "environnement clinique") → 03 Équipe opérationnelle (**pale, same `--about-bg` as 01** - no longer white) → Nous contacter (**navy, `--mp-navy`, same as Notre Mission** - no longer pale) → Nous soutenir (white), with the "Faites avancer l'innovation..." CTA staying navy as its own island inside the white Soutenir chapter. There is exactly **one** pale-blue token for backgrounds that need it in general: `var(--color-bg-tint)` (`#f3f7fc`) - never invent a second near-white shade **unless a pack explicitly asks for a second, more saturated step** (see subsection 02, which does exactly that via a derived value, not a new static token). **This rhythm inverted almost every background from the prior pass** (Vision was white, is now navy again; Chaire was white, is now pale; Équipe was pale, is now white; Contact was pale then white then pale again; the old dark "environnement clinique" became a light "écosystème" subsection) - when a new pack asks to "harmonize" or "fix" a background, re-read its FONDS section literally rather than assuming continuity with what an earlier design.md entry says, since this project's own owner has reversed these more than once.
- **A second, more-saturated pale-blue background, mechanically derived from a token rather than invented** (2026-08-28, subsection 02 "Un écosystème unique dédié à l'innovation" in `site/src/pages/index.astro`, `.about-v2__eco`): the pack asked for a background "nettement plus soutenu" than the site's one pale-blue token but still light and BOPA (not gray, not navy). Rather than adding a new static token, used the same OKLCH relative-color technique as `--bopa-filter-navy` (see the `color-mix`/OKLCH entry above): `oklch(from var(--color-accent) 0.89 0.045 h)`, defined as a local custom property (`--eco-bg`) on the component rather than in `tokens.css`, since it's a one-off mechanically-derived shade for a single section, not a reusable brand color. Verified concretely (not just trusted by eye) via canvas `fillStyle` + `getImageData` pixel sampling → resolves to `#c7ddf9`, WCAG contrast 11.6:1 against navy text - comfortably clears the 4.5:1 baseline. Candidates derived from `--bopa-cyan` instead were rejected as reading too turquoise/off-brand; the already-existing unused `--color-bg-tint-2` token was rejected as too subtle a step to satisfy "immediately visibly different." **When a pack asks for "a shade darker/more saturated than an existing pale background, same family," derive it from the relevant token with OKLCH relative syntax and verify the resulting hex/contrast numerically before shipping - don't eyeball a color and don't reach for a flat hex.**
- **Reusing a subsection's own title hierarchy for a sibling subsection: copy the CSS values into new, subsection-scoped classes rather than sharing the original classes.** Subsection 01 ("Chaire d'excellence") has its own number+divider+title marker classes (`.about-v2__chaire-number`, `.about-v2__chaire-marker-divider`, `.about-v2__chaire-marker-title`), explicitly documented as staying "propre à cette sous-section (01)" (see the "Une Chaire d'excellence" (01) - correctifs V4 entry). When subsection 02 was asked to "match 01's exact title hierarchy," the fix was new classes (`.about-v2__eco-number`, `.about-v2__eco-marker-divider`, `.about-v2__eco-marker-title`) with the *same* font-size/weight/line-height/color values, not literal reuse of the 01 classes - keeps each subsection's title free to diverge later without a shared-class ripple effect, consistent with how this file already treats icon arrays (`bandIcons`/`impactCardIcons`/`ecoIcons` are separate arrays despite an identical SVG convention).
- **"No background/card/shadow behind a row of stats, directly on the section's own background" is now a recurring, explicitly-requested pattern distinct from the navy stat-band component** (`.about-v2__chaire-band`, full-bleed navy with white numbers) used in subsection 01. Subsection 02's four stats (`.about-v2__eco-stats`) sit directly on `--eco-bg` with no wrapper background at all - just cyan numbers, navy labels, and thin `border-left` separators (`rgba(8,31,74,.2)`) - because the pack explicitly forbade any card/rectangle/dark band here. Don't default to wrapping a stats row in a band/card just because that's the established pattern elsewhere on the same page - check whether the specific pack asks for the bare version instead.
- **"Correctif Global" pack (2026-08-28) reversed the two-line title for subsection 03 back to one line, on the site's own established grounds** - the owner had earlier asked to align "03" with the wrapped title's first line (a real fix at the time), but this pack pointed out that 01/02's marker (number+divider+title, one line, full-width) is the real target hierarchy, and 03's version had only wrapped because its marker was nested inside the narrow *editorial column* rather than sitting in the full-width wrap above it like 01/02's. **Fix was structural, not typographic**: pulled `.about-v2__team-marker` out of `.about-v2__team-intro` into its own full-width row directly under `.wrap.about-v2__team`, and introduced a new `.about-v2__team-row` (the old `.about-v2__team` grid: `.72fr` intro / `2.28fr` cards, now `align-items: center`) to hold just the paragraph + cards below the marker - giving the title the full section width to fit on one line, matching 01/02 exactly. This also simplified the "center the paragraph against the cards" requirement: with the paragraph alone (no title) inside a grid using `align-items: center`, centering is free - no more flex-column-plus-auto-margins trick.
- **Reusing "harmonize X against the tallest of a set" pattern for the team cards' function→LinkedIn gap, this time with Elie Farha's card as the explicit named reference (2026-08-28, same pack)**: Farha's role text ("Directeur opérationnel de la plateforme BOPTECH") wraps to 3 lines - one more than Vibert/Hellec/Piguet's 2 - so even with an identical fixed `margin-top` on `.about-v2__linkedin` (already uniform from an earlier pass), LinkedIn still landed at different absolute heights per card, because the role text itself occupied different heights. Fix: `min-height` on `.about-v2__person-role` sized to Farha's own measured height (`4.28rem`, i.e. 3 lines at that font-size/line-height) so every card reserves the same role-block height regardless of its own text's actual line count - LinkedIn then lands at the exact same Y across all four automatically. **When a pack names one specific card/row as "the reference for this spacing," that's a signal the visible difference comes from a *content-length* mismatch (different line counts), not a CSS-value mismatch - the fix is almost always a `min-height` reservation sized to the named reference's own measured content, not a bigger/smaller margin.**
- **A `justify-content: center` added specifically to fix "ugly variable gap below short card text" (see the dated comment in `site.css` explaining exactly why) turned out to have a side effect nobody had connected until this pack: it desyncs title position across cards whose body text differs in length (2026-08-28, home "Nos innovations" project cards)** - a long description (LiverSight) leaves less slack above/below to distribute than a short one (Colette), so centering the h3+p block pushes titles to different Y positions per card. The original justification (avoid a growing empty gap under short descriptions) and the new one (align titles/descriptions across cards) are in direct tension, and only one can win with a single `justify-content` value - the owner's explicit alignment request took priority, so the rule was removed (reverting to default `flex-start`), which works cleanly here specifically because the media band above has a **fixed height** (184px) - every card's title starts at the same offset regardless of description length; the trade-off (short-text cards keep more empty space at the very bottom) was accepted implicitly by not being mentioned as a concern in this pack. **Before removing a rule that has a dated "here's why" comment, check whether the reason it was added and the reason it's now being removed are two ends of the same trade-off - if so, that's fine (priorities can change), but note the reversal explicitly rather than deleting the context silently.**
- **A "fixed" gap can still leave a second, invisible-from-the-component gap stacking right after it - always measure to the NEXT section's actual start, not just to the component's own wrapper edge (2026-08-29, same subsection 03 spacing saga)**: the previous fix made `.about-v2__team-band`'s own bottom edge sit exactly 91px below the cards (matching Nos innovations) - correct, verified, published - but the owner still saw "a large light space" afterward. The real culprit was one level up: `.about-v2` also carries the shared `.section-block` class, whose *generic* site.css rule adds its own `padding-bottom: clamp(5.5rem,10vw,9rem)` (144px at 1440px) - and `#qui-sommes-nous` only ever had `padding-top` overridden to fix an earlier issue, never `padding-bottom`. So the true gap the owner was scrolling through was `.about-v2__team`'s 91px **plus** this untouched 144px of generic section padding = 235px, invisible if you only inspect `.about-v2__team-band`'s own box (it ends cleanly; the extra pale space is the OUTER `<section>` continuing past it). Fix: `#qui-sommes-nous { padding-bottom: 0 }`, so the component-level padding is the only one governing the section's end. **When a spacing fix is verified correct at the component level but the owner still sees the old symptom, measure all the way to the NEXT visible section's actual start (`nextSection.getBoundingClientRect().top` vs the fixed element's bottom) - a shared generic class (`.section-block` here) can be silently adding a second padding on the parent that no amount of tuning the child fixes.**
- **Sticky-header-hide-on-footer, and a real, hard-won CSS lesson about transforming a `position: sticky` element (2026-08-28→29, "Footer-Header-Interaction-V1")**: built the site's first institutional footer (`.site-footer` in `Base.astro`, the shared layout - logo reused verbatim from the header, same 6 nav anchors, real contact/link URLs already used elsewhere, `--color-navy` background already documented as the deliberate Hero-matching bookend for this exact footer) plus the header-hides-near-footer interaction (IntersectionObserver on the footer, `rootMargin` scaled to the header's own measured height, header stays `position:sticky` throughout so there's zero layout shift). Two real CSS pitfalls surfaced while wiring the hide/show behavior, both worth remembering the NEXT time any "hide a sticky header via transform" task comes up:
  - **Giving a `transform` (or a `transition: transform`, even before any non-default value is ever set) to a plain, non-sticky ANCESTOR of a `position: sticky` element breaks that element's stickiness entirely** - it starts scrolling away with the page instead of pinning to the viewport. A wrapper div was tried specifically to hold the hide/show class (keeping the sticky header itself "untouched"), and this silently undid the sticky behavior across the whole page. Confirmed by measuring the sticky child's own `rect.top` against `-scrollY` (an exact match proves it's back in normal flow, not stuck). **A transformed ancestor changes the sticky element's positioning reference - this is real CSS behavior, not exotic. Never wrap a sticky element in a container that has (or will ever have) a `transform`.**
  - **On this project's tooling, once a `position: sticky` element has actually become "stuck" (scrolled past its natural position), `getComputedStyle()` and `getBoundingClientRect()` can both report stale, pre-change values for `transform` after a class or style change - even though the ACTUAL rendered paint is correct.** This was mistaken for "transform doesn't work on a stuck sticky element" through many rounds of testing, until `document.elementFromPoint()` (real hit-testing, not a cached style/layout read) at the header's old screen position returned page content instead of the header - proving the element genuinely had moved, contrary to what the introspection APIs claimed. A same-viewport screenshot (taken once actually near the top of a very tall page, where this tool's screenshot compositor is reliable - it silently returns a blank white image at deep scroll offsets, a separate, already-documented limitation) then visually confirmed both the hide AND the reappear-on-scroll-up behavior working correctly. **When `getComputedStyle`/`getBoundingClientRect` on a scrolled sticky element disagree with what a screenshot or `elementFromPoint` hit-test shows, trust the paint-based signal - the introspection getters are the ones that can be stale here, not the render.** The final code sets `element.style.transform` directly in the observer callback (not only a CSS class) specifically because a bare `classList.toggle()` was the version that measured as inert during this investigation - keeping both (class for the semantic/CSS hook, inline style for the guaranteed visual effect) costs nothing and removes the ambiguity for next time.
- **"Nous contacter" rebuilt to an exact reference PNG, including a first interactive canvas component on the site (2026-08-29, "Nous-Contacter-Exact-V1")**: content trimmed to exactly two intro paragraphs (second one partially cyan via a `.bopa-contact__highlight` span, same `--bopa-cyan` token used everywhere else) and a single "Nous trouver" address block - email and LinkedIn links removed entirely per explicit instruction, not just hidden. The location pin icon reused the *exact same* inline SVG already used for `ecoIcons[1]` in subsection 02 rather than drawing a new one - same convention (24×24, `stroke-width:1.6`, `currentColor`) already established for one-off icons in this file.
  - **First canvas-based interactive element on the site**: a small cyan point/line mesh in the bottom-left corner, delivered as a ready-made vanilla JS module (`contact-mesh.js`) + 4 lines of CSS - copied into `site/src/scripts/contact-mesh.js` near-verbatim (only reformatted, logic untouched) and wired via a plain `<script>` tag with an ES `import`, which Astro/Vite bundles automatically - no need to inline the whole function into the page. The module reads `--bopa-cyan` via `getComputedStyle` at draw time rather than hardcoding a hex, so it automatically stays on-brand if that token ever changes. It already ships with `prefers-reduced-motion` (falls back to a static frame), `IntersectionObserver`-based pausing when scrolled out of view, and `pointer-events:none` + a `mask-image` fade so it can never intercept clicks or fight with the text above it - a genuinely well-built self-contained component, not something built from scratch this time. **When a pack ships a working, self-contained script+CSS pair (no external deps, already respecting reduced-motion/perf), integrate it close to verbatim rather than rewriting it - the integration work is wiring (a script tag, a CSS import, a matching root element), not reimplementation.**
  - A `position:relative` (needed to host the absolutely-positioned mesh layer) and a `z-index:1` on the real content were already present on `.bopa-contact__inner` from earlier work - the pack's own reference CSS asked for a separate `.bopa-contact__content` wrapper class to do the same job, but adding it would have been a redundant no-op given the existing rule already covers it, so the class was left out of the markup. **Before adding a class a reference file wants "for stacking/positioning," check whether the element already has an equivalent rule - do not layer a second mechanism onto an existing one that already does the job.**
- **"Same padding token" does not mean "same visible gap" - a shared `var(--space-5)` bottom padding rendered two different amounts of actual whitespace under two card rows (2026-08-29)**: subsection 03's cards and "Nos innovations"' project rail both use `padding-bottom: var(--space-5)` (64px) on their section, and the owner asked for the visible space under 03's cards to match Innovations' - but measuring both live showed 64px vs 90.7px. The extra ~27px under Innovations isn't padding at all: `.bopa-projects-v2__inner` is a 2-column grid (intro text+CTA / card rail) with `align-items: center`, and the intro column is naturally taller than the rail, so centering leaves slack below the shorter rail on top of the section's own padding. Subsection 03's row has no such slack (its cards are the taller of the two columns, so the row's own bottom coincides with the cards' bottom) - same token, structurally different result. Fix: added the measured centering-slack delta directly to `.about-v2__team`'s padding-bottom (`calc(var(--space-5) + 1.7rem)`), landing within half a pixel of Innovations' real rendered gap. **When two sections share the same spacing token but a "make them match" request implies they still look different, measure the actual rendered gap on both (not just diff the CSS) - a layout mechanism (grid centering against unequal column heights) can silently add extra visible space that no padding value accounts for.**
- **Home section widths unified to 1320px, the day after the majority-vs-minority mistake (2026-08-29)**: the owner overrode her own earlier "match the majority" framing and gave a final, explicit call - Mission, Qui sommes-nous (01/02/03), Nous contacter, and Nous soutenir all now share Nos innovations/Notre Vision's `1320px`, so every major home section (bar Hero and the context-band strip, deliberately excluded as different kinds of layout) is one consistent width. Two real bugs surfaced while wiring this up, both worth remembering:
  - **`width` and `max-width` are independent properties that combine - they don't override each other, and "an earlier rule looks unused" is not the same as "it has no effect."** `.section-block .wrap` (site.css) has TWO rules on the same selector: one sets `max-width: var(--max-width)` (1184px), a later one sets `width: min(calc(100% - 3rem), var(--max-width))`. An earlier design.md-adjacent assumption ("first one is dead, later one wins") was wrong: both apply simultaneously - the `width` rule sets the preferred size, but the `max-width` rule still clamps it. Overriding just `width` with a bigger value (even with a more specific selector, even with inline `!important` - both tested) did nothing, because the old `max-width: 1184px` was still silently capping the result. Fix required setting BOTH `width` and `max-width` on the overriding selector. **Before concluding a CSS property override "isn't working," check whether a *different* property (most often `max-width` capping a `width`, or vice versa) from another still-active rule is the actual limiter - `el.style.setProperty(prop, val, 'important')` in the console is a fast way to test whether the property you're touching is even the bottleneck.**
  - This only affected "Qui sommes-nous" because it's the only home section that reuses the shared generic `.wrap` class (and therefore both generic site.css rules) - Mission/Contact/Soutenir/Vision/Innovations each have their own dedicated `__inner` class with no competing generic rule, so a single `width` override was enough for those. **When the same fix behaves differently across sections that "look similar," check whether they're actually built on the same underlying class/rule - a shared generic class carries baggage (here, a second competing property) that a dedicated per-section class doesn't.**
- **Picking the wrong reference section(s) when told to match "the other big sections" - verify against ALL of them, not just the first two you check (2026-08-28→29, "Notre Mission" width, corrected the next day)**: told to widen Mission's margins to match "les autres grandes sections," the first pass compared it only against Notre Vision and Nos innovations (both `min(1320px, 100%)`) and widened Mission to match - but never checked Nous contacter, Nous soutenir, or Qui sommes-nous, which all actually sit at `~1180-1184px` (`.bopa-contact__inner`, `.bopa-support__inner`, `.about-v2 .wrap`/`var(--max-width)`). Measuring all six at once (`getBoundingClientRect().width`/`.left` on each, same viewport) showed the TRUE majority is the narrower ~1180px group (3 sections) - Vision and Innovations are the two-section exception, not the rule - and Mission's original `1180px` had already matched that majority correctly before the "fix" touched it. The owner caught it by feel ("on dirait que tu as rétréci les autres en la prenant en référence") - widening Mission to match the minority pair made it stick out next to the majority, which reads as "everything else got narrower" even though nothing else's CSS changed. Reverted Mission back to `1180px`. **"Match the other sections" with more than two candidates on a page: measure every plausible candidate before picking which ones are "the reference" - two agreeing sections can still be the minority.**
- **"Match the end-of-section spacing you used for Notre Vision" required tracing past a dead-looking `clamp()` to find the rule that actually wins (2026-08-28)**: `.bopa-vision-v4`'s own component CSS sets `padding: clamp(4.75rem,7vw,7rem) 2rem clamp(5.25rem,8vw,7.5rem)`, and it's tempting to copy that clamp for "the same spacing" - but the ACTUAL computed `padding-bottom` on that section is a flat `64px` (`var(--space-5)`), because a higher-specificity ID selector (`#notre-mission[data-astro-cid-x], #innovations-bopa[data-astro-cid-x], #notre-vision[data-astro-cid-x] { padding-top: var(--space-5); padding-bottom: var(--space-5); }`) overrides the class rule's vertical padding entirely - confirmed by walking `document.styleSheets` in the browser and checking which rule the element actually `.matches()`, not by re-reading the component's own CSS block a second time. This ID-level rule is a known, deliberate pattern already documented once (`#qui-sommes-nous { padding-top: var(--space-5); }`, from an earlier fix whose own comment explicitly said "only the top is handled here - the bottom serves subsections 02/03, out of scope") - this request was that exact deferred bottom half, finally being done. Applied `padding-bottom: var(--space-5)` to `.about-v2__team` (not to `#qui-sommes-nous` itself) because the pale-blue band backgrounds (01/02/03) need the breathing room to stay INSIDE their own colored band - putting it on the outer section would add a mismatched-color gap between the band and the next section instead. **When asked to match another section's spacing "exactly," verify via computed style / matched CSS rules which declaration actually wins - a component's own written CSS is not proof of what it renders once ID-level or later overrides exist elsewhere in the same codebase.**
- **A 1px, 20%-opacity divider that reads fine in one context can be reported as "invisible" in another, even with identical CSS values (2026-08-28, subsection 03's marker divider)**: `.about-v2__team-marker-divider` was built with the exact same `width: 1px; background: rgba(8,31,74,.2)` as 02's proven, unflagged divider. A full DOM/CSS audit (computed style, bounding rect, `elementFromPoint`) confirmed the element genuinely existed, painted, and sat inside its column - nothing was structurally broken - yet the owner twice reported not seeing it. The working theory: 03's editorial column is narrower than 02's, its title wraps to two lines there and even overflows the column slightly, making the overall marker area visually busier - a hairline that reads fine against 02's cleaner single-line context can disappear in a tighter one. Fix: don't chase the theory further, just make the line unambiguously bolder - `width: 2px` (a whole pixel, not a fraction that can go fuzzy at some DPRs) and `rgba(8,31,74,.4)` (double the opacity). **When an owner reports an element as "not visible" and your DOM audit says it's technically present and correctly styled, trust the report over the audit - bump width/opacity/contrast decisively rather than re-verifying the same computed styles a third time.** Also: this session's Browser-tool screenshots reliably failed (returned solid white) for ANY scrolled-down position on this page, even a modest ~1000px scroll, while `getBoundingClientRect`/`getComputedStyle`/`elementFromPoint` checks kept working normally throughout - when a screenshot goes blank after scrolling but DOM queries still return sane, real values, treat it as a tool/compositor limitation for that session, not a page bug, and fall back to numeric DOM verification rather than fighting the screenshot tool.
- **A marker (number + divider + title) built with `align-items: center` silently breaks once the title wraps to more lines than the number/divider (2026-08-28, subsection 03's "03 | L'équipe opérationnelle")**: `.about-v2__team-marker` copied 02's marker CSS verbatim, including `align-items: center` - correct when the title is a single line (02's case), but 03's title sits in a much narrower editorial column (`.72fr` of the team grid, not the full-width wrap 02's marker lives in) and wraps to two lines ("L'équipe" / "opérationnelle"). Centering a short single-line number/divider against a tall two-line title pushes the number/divider down into the visual middle of the block - the owner saw this as "03 isn't level with 'L'équipe'" and "the divider disappeared" (it was still there, just centered awkwardly between two lines instead of sitting next to line 1). Fix: `align-items: flex-start` instead of `center` on the marker so the number and divider always align with the title's own top edge, i.e. its first line - regardless of how many lines the title wraps to. **When reusing a marker/heading pattern in a narrower column than the original, check whether the title will wrap there - `align-items: center` on a number+divider+title row only reads correctly when all three are the same number of lines; a narrower container is exactly where that assumption breaks first.**
- **A same-day follow-up (2026-08-28) pushed the team card photo further (33% → 50% of the card) and flipped "Nous contacter" to navy.** The photo ratio was re-derived the same way as the previous pass: measure the card's fixed body-content height (`bodyH`, effectively constant regardless of photo size since it's driven by text, not the photo), then solve for the `aspect-ratio` that makes `photoH == bodyH` (a 50/50 split) at the card's real rendered width - landed on `0.79/1` (measured 49.7%, close enough not to iterate further). **Nous contacter** went from the site's one pale-blue token to `var(--mp-navy)` - the same exact token as "Notre Mission," not a new shade - with every text/icon color inside it re-paired for the dark background by copying the values Mission already uses for the same job (`rgba(255,255,255,.94)` for primary body copy, `--mp-blue-bright`/`--bopa-cyan` for kickers/icons, unchanged) rather than inventing new opacities. The one thing that did NOT need touching: the contact form itself is a plain white floating card (`rgba(255,255,255,.98)` background) that already reads fine sitting on any section color - flipping a section to a dark background doesn't obligate re-theming a component that already floats above it as its own white surface. **When a pack or a live correction asks for "the same navy as section X," go find that section's actual custom property and reuse it - never eyeball a new dark blue, and copy its established text-color pairings wholesale rather than re-deriving opacity values from scratch.**

    A sixth variant, and the most consequential yet (2026-08-27, the "Notre approche" removal pass): `site.css` carried a whole legacy layer from the original "BOPA V2 flat backgrounds" pass - bare `#qui-sommes-nous { background: var(--color-navy); color: ... }`, `#soutenir { background: var(--color-bg-tint); color: ... }`, plus `#qui-sommes-nous h2/h3/p { color: #fff / near-white }` - that had silently survived *both* the "Qui sommes-nous" and "Nous soutenir" rebuilds. Because these are bare ID selectors (not compound with a class, unlike the already-known `#qui-sommes-nous.fade-to-navy`/`#soutenir.dark` variants that *were* checked and correctly found inert), they kept beating `.about-v2`/`.bopa-support`'s own class-based background and text colors the entire time - the live site had been rendering the whole "Qui sommes-nous" chapter as one solid navy block with white headings (instead of the intended light/dark alternation) and "Nous soutenir" with a light background (instead of navy) since each section's own launch commit, undetected until this later, unrelated cleanup pass happened to grep the same ids for another reason.     A seventh variant (2026-08-28, correctifs V4 on "Qui sommes-nous" subsection 01), two mistakes made together by the same root cause - a generic `.section-block` rule applying underneath a component that also carries that class: **(a) double-applied padding** - `.about-v2` carries both `.about-v2` (its own component class) and the generic `.section-block`, and `.section-block`'s own generic rule (`padding: clamp(5.5rem,10vw,9rem) 0`, site.css) already gives the section real top padding - `.about-v2__intro`'s own extra `padding-top` stacked on top of that unnoticed, roughly doubling the space before "Qui sommes-nous ?" compared with Mission/Innovations/Vision (which don't carry `.section-block` at all, so no equivalent stacking happens there). **(b) a `:not()` pseudo-class quietly outranks a plain compound class** - `.section-block:not(.hero) h2 { font-size: var(--text-xl); ... }` (site.css) was silently overriding a new `.about-v2__intro-title` rule sized to match Mission's H2 exactly, because `:not(.hero)` contributes its argument's specificity (one class), making the generic selector `class + class-equivalent + element` (0,2,1) - higher than a same-shape one-class component selector (0,1,0) and even most two-class ones (0,2,0). **Any new heading added inside a `.section-block`-classed component needs a selector at least as specific as `(0,2,1)` to reliably win** - prefixing with the section's own id (`#qui-sommes-nous .about-v2__intro-title`, `(1,1,0)`, an id always beats any count of classes) is the simplest reliable fix, cheaper than trying to out-count classes. Both bugs were only caught by comparing actual computed `paddingTop`/`fontSize` against Mission's own computed values side-by-side in the browser - reading either component's CSS in isolation looked correct in both cases.
    An eighth variant, same family again (2026-08-28, "finitions V2" on subsection 01): `.about-v2__intro-title`'s own `margin: 1.1rem auto 0` stacked on top of `.about-v2__kicker`'s shared `margin-bottom: 0.85rem` (the same tick-bearing eyebrow class Mission/Vision use), doubling the eyebrow-to-title gap to 31px measured, vs. Mission/Vision's real 13.6px. The fix was simply `margin: 0 auto` on the title - the eyebrow's own margin already *is* the correct, harmonized gap, so any spacing element placed right after it needs zero margin-top of its own, not "a little less than before." **Whenever a new element is placed directly after a shared, already-spaced component (an eyebrow, a kicker, a label), check whether that shared component already carries the trailing margin before adding any margin-top to the next element** - the default assumption should be "this is already spaced, add nothing," verified by comparing the measured gap against the same component's gap elsewhere on the site, not by eyeballing "looks about right."
    **Widening a CSS grid column does nothing if the child element inside it has its own smaller `max-width` (2026-08-28, same pass)**: asked to widen the "Chaire" text column to gain 1-2 lines, first tried loosening `.about-v2__chaire-foundation`'s `grid-template-columns` ratio (1.35fr→1.85fr) - measured **zero change** in line count, because `.about-v2__chaire-lede` itself already capped at `max-width: 42rem` (672px), narrower than even the *old* column width (734px) - the grid had room to spare the whole time; the paragraph's own cap was the actual bottleneck. Found by temporarily overriding the live DOM's inline styles in the browser (`element.style.maxWidth = 'Npx'` at several test values, recounting lines each time) before touching any file - a fast, safe way to find the real threshold before writing CSS. Raising the paragraph's own `max-width` to 50rem (800px) is what actually gained the line. **When "make this text column wider" doesn't change wrapping, check every ancestor AND the text element itself for a `max-width` - the narrowest one wins, and it's often not the one being edited.**
    A related but distinct find (2026-08-27, cyan-harmonization pass, not yet cleaned up): `site.css` has two separate base `.kicker { }` rules (one near the phase-tag styles, a second later one) with equal specificity - plain cascade order, not an id-vs-class collision - so the later one silently wins and the first's conflicting `color`/`display`/`margin-bottom` are dead code. Confirmed live via `getComputedStyle` on `boptech.astro`. Left alone for now since fixing it is layout/structure work, out of scope for a colors-only patch, and repointing both rules' colors to the same `--bopa-cyan` token happened to mask the visual symptom anyway - worth an actual cleanup pass (delete the dead first rule) next time `.kicker` itself is touched.
  - Don't paste a redesign pack's own absolute pixel/rem targets for a "slightly bigger" adjustment without checking they were baselined against *this project's current state* first - a pack's suggested Hero type sizes assumed a starting point that had already drifted from what's actually live (`.hero h1`'s min clamp value, specifically). Measure the actual current computed size in the browser, compute the requested percentage from that, and use the result - don't trust an absolute number handed over from outside the project, even when it looks close.
  - **Reusing a component across pages means reusing its custom-property scope too, not just its class name.** `.bopa-project-card` (site.css) reads `--mp-navy-deep`/`--mp-blue-bright`, which were only defined inside `.bopa-mission-v2, .bopa-projects-v2 { ... }` (the homepage sections that introduced it) - when `/innovations` reused the class for its own project grid (2026-08-27), the card rendered with a silently transparent background, because a CSS custom property has no value at all outside the scope that defines it (no cross-scope fallback, unlike inheritance). Fixed by adding the new page's own top-level class to that same definition list. Before reusing any `.bopa-*`/component class on a new page, check whether its styles reference a custom property, and if so, extend that property's defining selector to include the new page - don't assume the class alone carries everything it needs.
  - `.innovations-v2` (own `<style>` block in `innovations.astro`, importing categories/projects from `site/src/data/projects.js` rather than hardcoding them): the "Nos innovations" catalogue (H1 shortened from "Toutes nos innovations" 2026-08-27) - a dark-navy hero band (title + lead + Pré/Per/Post journey, `.innovations-v2__intro--dark`, `var(--mp-navy)`) that stops exactly before the filters, which sit in their own light `.innovations-v2__filters-band` below; then working tab filters (vanilla JS, `[data-project-filter]`/`[hidden]`, no reload), one row per category (icon + label + tagline aside, hairline-separated, no boxed frames) with `.bopa-project-card` vignettes reused verbatim from the homepage. Same "same exact component, more projects" instruction as the mission/projets pair above - don't fork a near-identical card style for a new page's project grid; extend the existing one's scope instead (see the custom-property note just above).
    **Splitting a dark/light background mid-grid (2026-08-27)**: the intro's title+lead and journey used to share one CSS grid with the filters nav (`grid-template-columns`, filters spanning `grid-column:1/-1` on its own row) so the dark background could be added. Coloring only *part* of a grid's rows isn't possible by styling a grid child alone - the fix was to pull the filters `<nav>` out into its own sibling container entirely (own light background), leaving the grid with just its original 2 real children (copy + journey), which also happened to simplify it (the `grid-column:1/-1` rule became dead weight and was removed). When a background needs to stop *between* two rows of the same grid, split the grid's children into separate sibling containers rather than trying to color part of a shared one.
    **A same-shape override can tie with the base rule instead of beating it (2026-08-27)**: `.innovations-v2__intro--dark h1 { color: #fff }` was written to override the base `.innovations-v2 h1 { color: var(--bopa-ink) }`, and looked like a bigger, later rule - but both are literally "one class + one element" in shape, so Astro's per-selector-segment scoping (`[data-astro-cid-*]` appended to *every* compound part on both sides) added identical extra weight to each, leaving them tied on specificity - and the tie went to the base rule, which happened to sit later in the file. The override silently lost and the title stayed dark on the new navy background. Fixed by chaining through a genuinely distinct intermediate class (`.innovations-v2__intro--dark .innovations-v2__intro-copy h1`, two real classes vs the base's one) rather than just repeating the outer-class-plus-h1 shape. **Counting "more classes in my selector" isn't enough to trust a specificity win - compare the actual shape against the specific rule being overridden, and verify the computed color/property in the browser, not just by eye.**
    On this page specifically (not the homepage), cards are deliberately non-clickable `<article>`s with no arrow - the owner's 2026-08-27 explicit call, since most of the 14 projects have no real destination yet and a whole-card link or a decorative arrow implies one. Only two projects get an explicit small inline text CTA instead (`.innovations-v2__card-action`, own class): LiverSight's video and the Compte-rendu card's Uncovr link, both real, both opening in a new tab. **The homepage's own `.bopa-project-card` instances lost their arrow too (2026-08-27, separate correctif)** - `.bopa-project-card__arrow` is now gone entirely (removed from markup and CSS), home-only; the two pages now converge on "no arrow," though for different reasons (interaction model vs. a pure visual-cleanup request). Home cards use `justify-content: center` on `.bopa-project-card__body` (scoped to `.bopa-projects-v2__rail`, since `/innovations` cards share the same class but must stay untouched) so shorter descriptions get a balanced gap top and bottom instead of one large gap piling up at the bottom where the arrow used to anchor content - a `margin-top`/`margin-bottom:auto` on the last flex child is a no-op here, since that's already exactly where default `flex-start` leaves the leftover space; centering is what actually redistributes it.
- Motion is subtle and purposeful, or absent. Never bouncy by default.

## Imagery

- Originals live in `source/brand/assets/` at full resolution; the site serves processed copies only (see the images section of `source/formats/website.md`). Python/PIL and ImageMagick are not available in this environment (see the PNG-transparency note below) - for the actual resize/re-encode/EXIF-strip step, use the `sharp` package already installed in `site/node_modules` (it's an Astro dependency): `node -e "require('sharp')('source/path.png').rotate().resize({width:2000,withoutEnlargement:true}).jpeg({quality:82}).toFile('site/public/path.jpg')"` - `rotate()` with no args auto-orients from EXIF, and `.toFile()` strips metadata by default.
  Typing an exact escape sequence or special character (a non-breaking hyphen `‑`, a regex Unicode range like `̀-ͯ`) directly into a source-file edit doesn't reliably land as the literal backslash-u text - it tends to come out as the already-decoded character instead, which looks identical in a diff summary but is a different (and for a regex, non-functional) set of bytes. Verify with `od -c` or Node's `.codePointAt()` after writing. If it comes out wrong, build the exact bytes deliberately instead of retyping: `printf` with explicit escapes (`\xNN` for raw UTF-8 bytes, or `\\u0300` with the backslash doubled) into a scratch file, then splice that file's content into the target via a small Node script - don't just keep re-editing the same spot hoping it lands differently.
- Photography for everything that can be photographed - the real team, real equipment, real procedures, not stock photos or staged compositions. Diagrams/schematics are fine specifically for explaining how a technical mechanism works (e.g. InMachina's "comment ça marche" schema, the "progrès" bridge diagram for the vision section) - that's a different job than illustrating a person, place, or object, and a photo can't do it. This flip-flopped twice already on InMachina (schema removed for a reused photo, then restored) - don't re-remove a diagram without asking.
  Same logic extends to stock-style illustrative images (Henri's AI-mascot artwork, Goldfinger's touchless-3D-model render, the Hepatgreen/coût financier/coût environnemental illustrations): fine for a project or concept that has no real BOPA photo opportunity yet (in-development tools, abstract economic/environmental framing, an AI assistant with no physical form) - not a general license to use stock photography once a real photo becomes possible.
  Hard exception, no flexibility: never put a stock/generic photo under a real named person's name (team cards, bios) - that's not "no photo opportunity yet", it's fabricating what a specific real individual looks like. Show initials in a plain avatar instead until a real headshot exists (see `.team-member-avatar`), and don't add a LinkedIn/social icon for someone without a real URL to point it at. The owner has since supplied real LinkedIn URLs for all four current team members (`.team-member-linkedin`, also recorded in `source/content/equipe.md`) - the rule was never "no icons ever", just "no icon without a real URL"; add one for a new person only once they give you their actual profile link.
- Checking whether a PNG actually has transparent pixels (not just RGBA format, which says nothing about whether any pixel's alpha is below 255): Python/PIL and ImageMagick are not available in this environment (only non-functional Windows Store stub aliases). Instead, load the image in the Browser tool via `javascript_tool`, draw it to a `<canvas>`, and read `getImageData()` - sample the four corners plus center for a quick check, or scan every pixel and report the opaque/transparent/partial split for a thorough one (see the `progres.png` and homepage-gradient investigation, confirmed genuinely transparent this way on 2026-08-25). This also proved the file was fine when the owner reported it "not background-less" - matched the existing caching-related "verify live, don't assume regression" pattern once again.
  That same diagram later had a real, different problem: the owner wanted its built-in "fondu" (fade) removed - the diagram's own artwork faded toward its right edge via a genuine alpha gradient (sampled: alpha 129 and 57 at two points well inside the artwork, not just edge antialiasing). Fixed by reading the raw pixel buffer with `sharp(...).raw().toBuffer({resolveWithObject:true})`, thresholding every 4th byte (the alpha channel) to 0 or 255, and re-encoding with `sharp(data, {raw:{width,height,channels}}).png().toFile(...)` - this makes anything with *any* visible content fully opaque while leaving true-transparent background alone. It does *not* fix fading caused by pale/light RGB color choices baked into the art itself (confirmed here: the right side stayed visually washed-out after the alpha fix, because those pixels were always a light blue, just now at full opacity) - that's a recolor, not a transparency fix, and isn't something to attempt without asking, since the "correct" un-faded color was never stored anywhere to recover.
  Outcome: the owner didn't want this trade-off - called the alpha-thresholded result "floue" (blurry, likely the loss of antialiasing at the fixed-alpha edges reading as lower quality) and asked to revert to the original file entirely, fade and all. Reverted with `git show <commit-before-the-edit>:<path> > <path>` for both the `source/brand/assets/` original and the `site/public/` served copy. Don't re-apply this alpha-threshold technique to this file again without asking first - it was tried and explicitly rejected once already.

## Responsiveness, learned the hard way

- A hover-lift/scale effect on a card inside a horizontally-scrolling row (`overflow-x: auto`, e.g. `.innovations-v2__cards`) gets silently clipped unless the row itself has enough padding: per spec, setting one overflow axis to anything but `visible` forces the *other* axis to compute as `auto` too, even if never set - so a row with `overflow-x: auto` and zero top/bottom padding clips vertically exactly where a lifted card's rest-state edge already sits (confirmed 2026-08-27: clearance measured 0px on all 14 `/innovations` cards before the fix). Give that row enough top/bottom padding to cover the transform distance plus the hover shadow's blur bleed (not just the transform) - and don't add it to a container that shares a grid row with something else (like a category label sitting beside it), since padding shifts the row's content relative to that sibling; verify actual clearance with `getBoundingClientRect()` (card top minus row top), not by eyeballing the CSS.
  Pair any hover-lift with `@media (hover: hover) and (pointer: fine) { ... }` around the `:hover` rule - without it, the effect can trigger (or get stuck on) a touch tap, which has no real "unhover" to end it. Verify with `window.matchMedia('(hover: hover)').matches` at each target width/device, not just visually.
- Every visual change gets checked at mobile width (~390px) and a normal desktop before publishing, and at ~2560px if the audience uses large screens.
- When adapting to large screens, scale whole modules together (type, dimensions, spacing, wraps). Scaling only headings leaves a small design floating in whitespace.
- Late CSS wins ties: media-query override blocks go at the end of the style block they override, or they silently lose the cascade. This has caused real bugs three times now (a mobile hero width, a mobile nav button that overflowed its menu, then the mobile nav *dropdown panels themselves* - `@media (max-width: 76rem) { .nav-dropdown-panel { visibility: visible; ... } }` sat before the unconditional base `.nav-dropdown-panel { visibility: hidden; }` in `site.css`, so the base rule always won and the mobile menu's dropdowns never actually opened, on any phone, until someone opened one and looked). That third case broke functionality, not just looks - a layout glitch is easy to spot scrolling past it, a menu that silently never opens is not, unless someone actually taps it. When adding *any* mobile/responsive override for a selector that already has an unconditional rule elsewhere, place the `@media` block immediately after that rule (not wherever feels natural in the file), and verify the computed style at the target width, not just that the code looks right.
  Verifying this one is itself tricky in this environment: reading `getComputedStyle` immediately (or even after a `setTimeout`) on a property that's mid-`transition` can report stale values when the Browser pane isn't actually displayed/compositing frames (a real, separate limitation seen throughout this project - screenshots fail with "the page is not compositing frames" when the pane is backgrounded). Don't conclude a transition-driven show/hide is broken from a hidden-tab computed-style read alone; either front the tab first, or test a state reached via `transition: none` (as the mobile nav override already sets) where the computed value can't lag behind the class change.
  **This turned out to go further than just `:hover`/transitions (2026-08-27, header scroll-offset correctif): when the pane isn't composited, `getBoundingClientRect()`/`getComputedStyle()` can report stale, frozen layout values even for a plain, non-transitioning property changed via an inline `style.setProperty(..., 'important')`** - about as forceful a style write as exists, and it still didn't move the measured height. A *fresh page navigation* (not a JS mutation on an already-loaded page) reliably reflects real CSS values even while uncomposited, though - confirmed by cross-checking a value derived two independent ways (measured header height at rest, and computed from the source CSS's own padding/logo-height numbers) and getting the same answer to sub-pixel precision at two different breakpoints. **When you need a layout measurement in this environment and can't get the pane composited, prefer reading values off a fresh navigation over triggering a mutation with JS and re-measuring - and where possible, cross-check the measurement against a hand-computed expectation from the CSS source rather than trusting a single reading.**
  Same underlying limitation showed up a different way (2026-08-27, "Notre vision" pass): after using `resize_window` with `preset: "mobile"` then `"desktop"` earlier in a session, a later `preset: "desktop"` call left `window.innerWidth`/`innerHeight` reading `0` and every responsive check computed against the *mobile* breakpoint despite the preset claiming to restore desktop - because the pane wasn't actually displayed at that moment, so it had no real size to "return to." Explicit pixel dimensions (`resize_window` with `width`/`height`, e.g. 1440×900) forced a real viewport and immediately fixed it. If a responsive computed-style check ever comes back for the wrong breakpoint, suspect the pane's display state before suspecting the CSS - re-check with explicit width/height rather than a preset.
- **A `min(Xvw, Yrem)` container width and a `clamp(min, Xvw, max)` font-size inside it can silently decouple** once the viewport gets narrow enough that the font hits its floor: the font stops shrinking, but the `vw`-based container keeps shrinking with it, so the available width per line keeps dropping while the text doesn't get any smaller to compensate. Hit this 2026-08-27 harmonizing the Hero lede to Notre Mission's type scale: a `.nowrap`-locked compound word ("hépato-bilio-pancréatique") that fit on 3 lines at both ~700px and ~1440px viewports still wrapped to a 4th line specifically in the ~1024px range between them, because that's exactly where the font sits at its `1rem` floor but the `min(vw, rem)` column width is still shrinking. A pure `vw` ratio increase doesn't fix this (verified: pushing the ratio right up to the container's own outer limit still wasn't enough at 1024px) - the fix is a `max(Nrem, min(Xvw, Yrem))` floor, an absolute minimum width that holds through the floored-font range, layered under the existing vw/rem clamp for wider screens. When a pack asks to reuse another element's exact type scale, don't just test the width-sensitive result at the two ends of the responsive range (narrowest and widest) - the floor-crossover point in the *middle* is where this kind of thing breaks, and it won't show up unless you specifically check the width where the font's own clamp bottoms out.
  The same decoupling bites in the *opposite* direction too, and is worse to catch because "wider screen = more room" feels intuitively safe. `.context-band`'s items live inside `.section-block .wrap`, which is capped at `var(--max-width)` (74rem) - past ~1232px viewport, the wrap (and every item inside its grid) stops growing at all, width frozen. But `.context-text` still used a `clamp(min, Xvw, max)` font-size keyed to raw viewport width, so past that same point the *font* kept growing toward its ceiling while the *column* had already stopped - confirmed 2026-08-27: the CHB fragment fit fine at 1260px but overflowed its own column by 52px at 1920px, despite 1920px being "more room." Once a container's width is capped independent of the viewport (a `min(vw, rem)` or a `max-width` token, not just "the whole page"), any font-size inside it needs the same cap logic (a flat value, or a `clamp` capped to the *container's* plateau point, never raw `vw` alone) - check the widest realistic viewport explicitly, not just "wide enough that it must be fine."
- Never put a standard CSS property and its `-webkit-`-prefixed twin (`backdrop-filter`, `mask-image`, etc.) as two declarations in the *same* rule - the production build's CSS minifier treats them as redundant duplicates and silently drops one (whichever came second in source), breaking whichever browser needed the dropped one. Put the `-webkit-` version in its own rule instead, guarded by `@supports not (<property>: <value>)`. This is a build-output bug, invisible in the dev server and in the source - the only way to catch it is to grep the actual files in `dist/` after `npx astro build`.
- Same "works in dev, breaks in the real build" trap for Node frontmatter code: don't resolve a filesystem path with `new URL('../relative/path', import.meta.url)` in a page's frontmatter - the production build bundles that file into `dist/.prerender/chunks/`, so the relative path resolves against the wrong location and throws `ENOENT` at build time even though `astro dev` never showed a problem. Use `path.join(process.cwd(), ...)` instead (stable in both modes, since `cwd` is always the `site/` root when running `astro dev`/`astro build` from there). Any page doing filesystem work (like the team gallery's `readdirSync`) needs an actual `npx astro build` run before shipping, not just a dev-server check.
- `.wrap`'s max-width/centering is defined as `.section-block .wrap` (site.css) - a descendant selector, not a standalone class. An element placed *between* two sections (not nested inside either one - e.g. a card straddling a section boundary with a negative margin) gets `class="wrap"` but silently stretches to the full viewport width, since the scoped rule never matches it. Give it its own explicit `max-width: var(--max-width); margin-left: auto; margin-right: auto;` (plus a `calc(100% - 2 * var(--space-4))` width so it still keeps edge padding below the max-width breakpoint) instead of assuming `.wrap` alone is enough.
- Adjacent `.section-block`s stack their padding-top + padding-bottom into a gap that reads as too big (default `--space-6` top and bottom = 16rem combined). Check every new section junction for this; the fix already used several times is `padding-bottom: var(--space-5)` on the section above and `padding-top: var(--space-5)` on the one below.
  This had only ever been fixed junction-by-junction as each one got touched for some other reason - by 2026-08-25 that left several *older* junctions still at the untouched default (`#projets` → `#equipe` and `#equipe` → `#soutenir` were both still 256px combined, worse than the ones already "fixed"). When the owner says spacing feels too big "in general" rather than pointing at one spot, measure every section's computed `padding-top`/`padding-bottom` on the live page and tighten every junction to the `space-5`/`space-5` standard in one pass, not just the one that prompted the complaint.
  Same over-stacking can happen *within* one section too, not just between two: the projects page's intro (kicker/h1/lede) → `.phases-image` → first `.section-sub` had two separate `margin-top: var(--space-5)` gaps back to back (one before the diagram, one after) - each looked fine alone but together, plus the diagram's own height, read as too much empty space before any project actually appeared. Tightened both to `var(--space-4)`. When several elements in a row each carry their own top margin, judge the *sum* against the page, not each margin in isolation.
  `.section-sub` is a page-scoped class redeclared separately in both `index.astro` and `innovations.astro` (Astro doesn't share page-scoped styles - see the component inventory note above). Tightening it in one page's `<style>` block does nothing for the other's identically-named copy: `innovations.astro`'s got fixed first, and `index.astro`'s sat at the untouched `var(--space-6)` default for a full extra session before the owner reported the same "too much blank space" complaint a third time and it turned out to be this. When a spacing fix applies to a class name that exists on more than one page, grep for every page-scoped redeclaration of it and check each one, not just the page you're currently looking at.
- A `vw`-based width tuned for desktop (to track some other element's own `vw` sizing) silently caps that same element at a fraction of the screen on mobile too, with no visual warning - it just quietly shrinks. Anything sized in `vw` needs an explicit check at ~375px, not just at desktop widths; the hero's text column once capped itself at 50vw on a phone (half the screen, for no reason - there was no second column to leave room for).
- No split screens or side-by-side columns on phones - single column, full width, always. When adding a new two-column layout, its mobile collapse is not optional and needs verifying at ~375px before publishing, not assumed from the desktop code.
- Same idea one level down: a flex item with no explicit width (`.stat-row .stat` - just three items in a `flex-wrap` row) looks fine on desktop where there's room, but on a phone `flex-wrap` gives each item only as much width as its own content needs, which isn't enough for a label like "Mécénat collecté depuis 2020" to fit on one line. Any flex/grid item holding text that must stay on one line needs an explicit mobile width (`flex: 1 1 100%` here, stacking the three vertically), not just "let it wrap and hope."
- One session surfaced six separate mobile bugs at once (nav menu, gradient anchors, heading hierarchy, stat sizing, pipeline text-align, and the lede size-cascade above) - each was real and each was found only by actually loading the page at ~375px and checking, not by reading the desktop CSS. None of them were visible from the code alone; several had shipped across multiple earlier sessions without anyone catching them until the owner did. Takeaway: a mobile check is not "does this one new thing collapse" - it's worth periodically loading the *whole* page at 375px, section by section, rather than only checking whatever was just touched.
- **Superseded 2026-08-27, do not reintroduce**: an earlier phase of this project built a continuous white-to-cold-blue `main` gradient plus `mesh-echo`/`ambient-halo` decorative overlays meant to make section boundaries invisible. The owner had an external redesign done (ChatGPT, working from a full export of the homepage) that deliberately reverses this: **flat, hard-edged section backgrounds** (each `#section-id` gets one solid/tinted color from `tokens.css`, see the "BOPA V2" override block at the end of `site.css`), no gradients, no halos, no mesh echoes. The rupture between sections is now the point, not something to hide. If a future request asks to "smooth out the transitions between sections" again, flag the contradiction with this rule rather than silently reintroducing gradients - it was tried, it worked, and it was explicitly replaced.
- **Phase/step colors are blue-only, no exceptions**: `--color-step-1/2/3/4` all live inside the BOPA blue family now (cyan → medium blue → deep blue → navy). An earlier version used green/purple/amber for visual variety across pré/per/post-opératoire and médico-économique; the redesign explicitly banned any green, purple, or orange anywhere in the UI. Don't reach for an off-palette accent color for "variety" even when tempted - vary weight, size, or blue shade instead.
- Buttons across the site (`.btn-outline-premium` / `.btn-filled-premium`, used by the Hero, header CTA, and section CTAs) are a **rounded rectangle** (`var(--radius-md)`, ~10px), not a pill - a mid-session mistake gave the header CTA `border-radius: 999px` before the owner corrected it back to match the Hero's actual shape. The base `.btn` class defaults to a pill on its own; every context that uses the premium variants needs its own `border-radius: var(--radius-md)` override (see `.hero-actions .btn`, `.site-header nav > a.btn` in `site.css`) - don't assume the base class's shape is what ships.
- **"Inspect this button's current hover CSS" means every class on the element, not just the one that looks most specific to it (2026-08-27, V4.1 button-hover-harmonization pack).** The header "Nous soutenir" button (`class="btn nav-cta btn-filled-premium"`) was named the reference for all cyan CTA hovers; reading only `.btn-filled-premium:hover` (background + box-shadow) missed that the shared base `.btn:hover` rule *also* applies to this element and contributes an uncontested `transform: translateY(-2px)` - the two rules don't conflict on `transform`, only on `box-shadow` (where `.btn-filled-premium:hover`, later in source, wins). The real, rendered hover is the union of both rules, and the lift would've been silently dropped from the two buttons being harmonized to match it had a first pass (copying only the box-shadow/background) not been caught by re-deriving the cascade from the stylesheet rather than trusting an initial skim. **When told to copy a button's "current hover behavior" exactly, list every class on that element, find every `:hover` rule that matches any of them, and resolve the union/conflicts by specificity + source order - don't assume the class most specific to the button's *name* is the only rule in play.**
  Verifying this in the browser tool turned out to be unreliable here: forcing `:hover` via the `computer` tool's hover action made `element.matches(':hover')` report `true`, but `getComputedStyle` kept reporting resting-state values (background, box-shadow, transform all unchanged) even after waiting - consistent with this project's known "the Browser pane isn't composited, so paint-dependent state doesn't update" limitation (see the Responsiveness section below), just extended to `:hover` specifically. **Don't trust a hover computed-style check in this environment - verify by reading the stylesheet's cascade (which classes apply, which rules match, which wins) instead**, the same way a `getBoundingClientRect` layout check stays reliable while a screenshot doesn't.
- Cards (`.card`) got flatter in the 2026-08-27 redesign too: translucent white (not opaque), a thin 1px border, no drop shadow at rest (a small lift + soft shadow only on hover). Section-level contrast now comes from the flat background colors themselves, not from card depth - don't add shadow/gradient back into cards to make them "pop" against a flat section; that's fighting the new system, not completing it.
- Body paragraphs are **left-aligned**, not justified - this reverses an earlier rule (justify was tried, tuned, and used for months of this project). The 2026-08-27 redesign explicitly calls out justified text as worse for web readability. If any component-specific `text-align: justify`/`hyphens: none` rule surfaces during a future edit, remove it rather than preserve it; the global rule is now `p { text-align: left; line-height: 1.72; }` in the "BOPA V2" block of `site.css`.
- Collapsed accordions (`<details>`) are for secondary/supplementary detail, not for a page's primary content - BOPtech's named projects (InMachina, Salle Hybride) were once the last thing on the page, hidden behind a click. Primary content goes early and stays visible by default.

## Accessibility baseline

- Text over background always passes contrast (4.5:1 for body text).
- Every meaningful image has real alt text.
- The site works with keyboard only; interactive elements are actual links and buttons.
