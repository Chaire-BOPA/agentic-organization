# Design guide

How we look, everywhere: the website, the decks, any image we produce. The AI reads this plus `tokens.css` before any visual decision. The setup skill personalizes it; after that it grows one rule at a time.

## Philosophy

Institutional but alive: a hospital-and-engineering research chair, not a startup. Confident, restrained, generous whitespace, one big scrollable home page. Inspired by owkin.com and whitelabgx.com — mostly light, clinical-clean sections, punctuated by a couple of full-bleed dark-blue blocks for emphasis rather than color everywhere. Every visual decision should be defensible against this paragraph.

## Tokens

`tokens.css` is the only place where colors, fonts, and the spacing scale are defined. Nothing in `site/` or in a deck hardcodes a hex value, a font name, or a magic pixel number. Adding a design idea that needs a new value means adding the token first, with a name that says what it's for.

- **Color**: the BOPA logo's four blues (`--bopa-blue-1..4`) are the source. `--color-accent` is the darkest (`--bopa-blue-1`, best contrast on white); `--color-dark` is a deeper navy used only for full-bleed emphasis sections (hero, one spotlight section per page — not every other section). Neutrals are cool-toned to sit with the blues: a light blue-gray `--color-bg`, deep navy `--color-ink` instead of pure black.
- A solid `--color-accent` fill on a dark navy section reads as neon, not premium. But buttons still need a visible contour there, not bare text either - the "Faire un don" CTA went from solid fill, to plain text-only, to its current form: `.btn-outline-premium` (dark translucent fill + white inset outline + white text), the same reusable class the hero buttons use. That's the standard treatment for a button on a dark section here.
- **Type**: still system fonts (no webfont chosen yet), but display headings use `font-weight: 700` and `--tracking-tight` (-0.02em) to read as confident and current rather than default browser serif. Revisit if the owner picks a webfont.
- On light sections, a short tagline/label defaulting to plain navy ink or gray reads as flat - the owner asked for the partners tagline to be "plus peps" (livelier) and in blue. Fix was `color: var(--color-accent)` (not `--color-ink`/`--color-muted`) plus a size bump on the tagline itself. When a short standalone line of text feels too quiet, brand blue plus a touch more size is the default fix to reach for before inventing a new treatment.
  That size bump then broke the phrase's wrap inside its narrow fixed-width column (`.partners-text`, 11rem) - "Ensemble, innovons sans limites" wrapped across 3 lines and looked messy, and the owner specifically wanted "innovons sans limites" kept together as one unit. Fixed by wrapping each half in its own `<span>` with a forced `<br />` between them (not relying on the natural wrap point, which drifts with column width/font changes) and setting `white-space: nowrap` on the whole line so a future width change can't silently re-wrap it. When forcing a specific line break in a heading/tagline, always verify with `scrollWidth` vs `clientWidth` that the intended one-line half doesn't itself overflow at the column width you land on.
  Getting the line break right didn't settle it, though - a two-tone color split on the two halves still read as flat to the owner ("still don't like it"), three separate color/size passes in. What actually landed: stop treating it as a type problem and give the block its own visual presence instead - a soft gradient backdrop (`linear-gradient(135deg, color-mix(... var(--color-accent) 12%, transparent), transparent 75%)`) plus a left accent bar, i.e. a highlighted callout rather than plain text next to a logo strip. If a repeated "make this text pop" request survives two or three color/size iterations without landing, that's a signal the fix isn't a text property at all - reach for a backdrop/border/card treatment on the container next, rather than a fourth type tweak. (Practical trap hit while doing this: adding `padding` to an element that already has a fixed `max-width` shrinks its *content* width by the padding amount under the default `border-box` sizing, which reintroduced the overflow this section just fixed - widen the `max-width` by roughly the new padding whenever you add padding to something with a pre-tuned width.)

## Type

- Display face and text face are both the system sans stack for now (`--font-display` / `--font-text` in tokens) — no webfont has been chosen. If the owner picks one, self-host it (put files in `site/public/fonts/`, declare with `font-display: optional`) so the site never flashes or jumps on load.
- One type scale, defined in tokens, used everywhere. Resist per-page font sizes.
- `--text-xl` is a `clamp()` and already scales down on narrow screens; `--text-2xl` (used by the base `h1` and `.stat-row .stat-value`) is a flat `3.25rem` with no floor. On a phone that left the page `h1` (innovations/boptech/publications - the homepage's own `.hero h1` already had its own clamp) *smaller* than `h2` (both bottoming out, but `h1`'s fixed value has no floor to hit while `h2`'s clamp does), and left the "Nos projets et réalisations" stat numbers (1.6M€, etc.) at a fixed 52px - roughly 14% of a 375px screen for one short string. Both are now `clamp(2rem, 6vw, var(--text-2xl))`, unchanged above ~866px wide. Any *other* place using `--text-2xl` directly needs the same check before it ships - a flat value on a large-scale token is a mobile bug waiting to be noticed.

## Layout and components

- Generous whitespace; when in doubt, remove an element instead of shrinking everything.
- Build a small set of components and reuse them. Keep an inventory here as they appear, with a pointer to where each lives. A new page should mostly assemble existing components.
  - `.section-block` (+ `.dark` variant): full-bleed section wrapper used to build the scrollable home page — see `site/src/styles/site.css`.
  - `.kicker`, `.lede`: small uppercase label above a heading, and a larger intro paragraph below it. `.lede` is sized for a short, punchy 1-2 sentence intro - it's not "the paragraph right under an h2" by default. The "Nous soutenir" paragraph (3 full sentences of running text) was styled `.lede` simply because of its position and read as oversized once it was actually read at that size; moved to a plain body-size class. Pick the class by the text's length/role, not by where it sits.
  - `.card-grid` / `.card`: simple bordered cards, used for the projects sections. Cards in the same row stretch to equal height on desktop by default (grid `align-items: stretch`) - no mobile override needed, `auto-fit` already collapses multi-card rows to one column there. When a card has a photo/video, make `.card` a flex column and give the media `margin-top: auto` so it lands flush at the bottom instead of leaving slack below it.
  - `.team-member-card` / `.team-member-avatar`: person cards for "Notre équipe" - dark navy cards, initials-in-a-circle instead of a photo when no real headshot exists yet (see the imagery rule below on why). Owner wants these narrow, all four in a single row rather than 2x2 - tight horizontal padding (`var(--space-2)` sides) and a smaller `.team-member-name` (`--text-sm`, `white-space: nowrap`) keep every name on one line at that width; check `scrollWidth` vs `clientWidth` in the browser if a longer name gets added later, since `nowrap` overflows silently instead of wrapping. `.team-member-credentials` (PhD/MD, only some people have one) always renders its `<p>` even when empty, rather than conditionally omitting the element - a row of cards where some have an extra optional line and others don't pushes every *following* line (role, here) to a different height per card, reading as "misaligned" even though each card is internally correct. Same fix applies to any future per-card optional field in a row of otherwise-identical cards. That fixed the text rows, but the trailing `.team-member-linkedin` icon still floated at a different height per card, because *variable-length content above it* (the role text wraps to a different number of lines per person) pushes it down by a different amount on each card, even with every text row now the same height as its counterpart. Same fix as `.card`/`.card-photo` above: made `.team-member-card` a flex column and gave the icon `margin-top: auto` so it's pinned flush to the card's bottom edge regardless of how much wrapped role text sits above it. General rule confirmed twice now: anything meant to line up across a row of cards needs to be pinned to a fixed edge (top or bottom via flex), not just placed after variable-height content and hoped into alignment. Real headshots now have a path in: drop a file into `site/public/images/team-photos/` named after the person's slug (accents/titles stripped, lowercased, hyphenated - see `slugify` in `index.astro`) and their card swaps the initials avatar for the real photo automatically; `source/brand/assets/team-photos/README.md` is the owner's drop-zone doc. This is what the "until a real headshot exists" clause in the imagery rule below was waiting on - use it instead of ever placing a stock photo under a name. All four team members now have real photos (2026-08-26); the owner's uploads to `source/brand/assets/team-photos/` were named by first name only (`axelle.png`, not `axelle-piguet.png`) rather than the full slug the README asks for - processed and renamed to the correct slug by hand rather than asking for a re-upload. Don't assume an upload's filename already matches the expected slug; check and remap instead of erroring or waiting on the owner to rename it. Squares resized with sharp's `resize({width, height, fit: 'cover'})` (not just relying on the circle's own CSS `object-fit: cover`) so the served file itself is already a tight square, not a full-size photo the browser crops down every time.
  - Two-column intro split (`.equipe-layout` / `.equipe-intro` / `.link-arrow` in `index.astro`): fixed-width text column (kicker, heading with an accent-colored second line, lede, an arrow link) beside a content column (cards, media). Built from an owner-supplied reference screenshot for "Notre équipe" - reuse this split for any future section the owner points at a similar mockup, rather than the older pattern of stacking the text block full-width above the content. Collapses to one column (text first) below `64rem` - same no-split-screens-on-mobile rule as everywhere else.
  - `.logo-grid`: partner logo wall, used by the partners section.
  - `.stat-row`: big number + label, used by the publications section.
  - `.nav-dropdown`: `<details>`-based dropdown menu, used by the two top-nav groups (La Chaire, Innovations).
  - Auto-advancing crossfade carousel (dots, pause on hover/focus, restart timer on manual navigation): the homepage's project carousel (`#project-slider` in `index.astro`) is the reference implementation. Good for a case that genuinely needs one-at-a-time reveal (e.g. distinct project pitches). Not automatically the right tool for "N photos of the same kind" - the team photo gallery copied this pattern at first and the owner rejected it (2026-08-25): full-width made a single photo feel oversized, and the small corner dots were too easy to miss to find as a navigation control at all. Swapped for a plain `.team-gallery-grid` (CSS grid, `auto-fit`/`minmax`) showing every photo at once, smaller, nothing to browse. Default to a static grid for "here are our photos" content; reach for the carousel only when one-at-a-time is the actual goal, not just because a similar feature exists elsewhere.
  - A gallery that should grow without a code change: read the folder with `readdirSync` in the page frontmatter instead of hardcoding a list (see the team gallery) - any file dropped into the matching `site/public/images/...` folder becomes a slide automatically. Pair with a README in `source/brand/assets/<name>/` telling the owner where to drop their own originals.
  - Any number quoted on one page that's really a count of content defined on another page (e.g. the homepage hero's "projets innovants" stat vs. the actual project list on `/innovations`) belongs in a shared module under `site/src/data/` (see `projects.js`), imported by both pages, with the number computed (`.reduce`/`.length`), never hand-typed on the second page. A hand-typed copy *will* drift the next time a project is added or removed on the other page - this one was already wrong (said 15, real count was 14) before anyone noticed.
  - A page's own `<h1>` can silently drift from the label the nav uses to link to it - the innovations page's nav entry (`Base.astro`) already said "Nos projets" while its own `<h1>` still said "Nos innovations", unnoticed until the owner pointed it out. When touching a page's `<h1>`/`<title>`, cross-check it against how `nav` in `Base.astro` labels the link that points there.
- Motion is subtle and purposeful, or absent. Never bouncy by default.

## Imagery

- Originals live in `source/brand/assets/` at full resolution; the site serves processed copies only (see the images section of `source/formats/website.md`). Python/PIL and ImageMagick are not available in this environment (see the PNG-transparency note below) - for the actual resize/re-encode/EXIF-strip step, use the `sharp` package already installed in `site/node_modules` (it's an Astro dependency): `node -e "require('sharp')('source/path.png').rotate().resize({width:2000,withoutEnlargement:true}).jpeg({quality:82}).toFile('site/public/path.jpg')"` - `rotate()` with no args auto-orients from EXIF, and `.toFile()` strips metadata by default.
  Typing an exact escape sequence or special character (a non-breaking hyphen `‑`, a regex Unicode range like `̀-ͯ`) directly into a source-file edit doesn't reliably land as the literal backslash-u text - it tends to come out as the already-decoded character instead, which looks identical in a diff summary but is a different (and for a regex, non-functional) set of bytes. Verify with `od -c` or Node's `.codePointAt()` after writing. If it comes out wrong, build the exact bytes deliberately instead of retyping: `printf` with explicit escapes (`\xNN` for raw UTF-8 bytes, or `\\u0300` with the backslash doubled) into a scratch file, then splice that file's content into the target via a small Node script - don't just keep re-editing the same spot hoping it lands differently.
- Photography for everything that can be photographed - the real team, real equipment, real procedures, not stock photos or staged compositions. Diagrams/schematics are fine specifically for explaining how a technical mechanism works (e.g. InMachina's "comment ça marche" schema, the "progrès" bridge diagram for the vision section) - that's a different job than illustrating a person, place, or object, and a photo can't do it. This flip-flopped twice already on InMachina (schema removed for a reused photo, then restored) - don't re-remove a diagram without asking.
  Same logic extends to stock-style illustrative images (Henri's AI-mascot artwork, Goldfinger's touchless-3D-model render, the Hepatgreen/coût financier/coût environnemental illustrations): fine for a project or concept that has no real BOPA photo opportunity yet (in-development tools, abstract economic/environmental framing, an AI assistant with no physical form) - not a general license to use stock photography once a real photo becomes possible.
  Hard exception, no flexibility: never put a stock/generic photo under a real named person's name (team cards, bios) - that's not "no photo opportunity yet", it's fabricating what a specific real individual looks like. Show initials in a plain avatar instead until a real headshot exists (see `.team-member-avatar`), and don't add a LinkedIn/social icon for someone without a real URL to point it at. The owner has since supplied real LinkedIn URLs for all four current team members (`.team-member-linkedin`, also recorded in `source/content/equipe.md`) - the rule was never "no icons ever", just "no icon without a real URL"; add one for a new person only once they give you their actual profile link.
- Diagram PNGs (progrès bridge diagram, phases timeline) placed on their own between paragraphs shouldn't be full section width, but don't overcorrect either - a first pass at `70%/max-width: 40rem` for both got called too small for both (worse for the phases timeline, the page's lead visual, than for the vision diagram). Landed on `.approche-image` at `85%/max-width: 48rem` and `.phases-image` at `100%/max-width: 56rem` - the two diagrams don't have to match each other's size, size each to how central it is to its own page. Both still go full-width below `40rem` (mobile), where any percentage smaller than 100% starts making the diagram's own text labels hard to read.
- Checking whether a PNG actually has transparent pixels (not just RGBA format, which says nothing about whether any pixel's alpha is below 255): Python/PIL and ImageMagick are not available in this environment (only non-functional Windows Store stub aliases). Instead, load the image in the Browser tool via `javascript_tool`, draw it to a `<canvas>`, and read `getImageData()` - sample the four corners plus center for a quick check, or scan every pixel and report the opaque/transparent/partial split for a thorough one (see the `progres.png` and homepage-gradient investigation, confirmed genuinely transparent this way on 2026-08-25). This also proved the file was fine when the owner reported it "not background-less" - matched the existing caching-related "verify live, don't assume regression" pattern once again.
  That same diagram later had a real, different problem: the owner wanted its built-in "fondu" (fade) removed - the diagram's own artwork faded toward its right edge via a genuine alpha gradient (sampled: alpha 129 and 57 at two points well inside the artwork, not just edge antialiasing). Fixed by reading the raw pixel buffer with `sharp(...).raw().toBuffer({resolveWithObject:true})`, thresholding every 4th byte (the alpha channel) to 0 or 255, and re-encoding with `sharp(data, {raw:{width,height,channels}}).png().toFile(...)` - this makes anything with *any* visible content fully opaque while leaving true-transparent background alone. It does *not* fix fading caused by pale/light RGB color choices baked into the art itself (confirmed here: the right side stayed visually washed-out after the alpha fix, because those pixels were always a light blue, just now at full opacity) - that's a recolor, not a transparency fix, and isn't something to attempt without asking, since the "correct" un-faded color was never stored anywhere to recover.

## Responsiveness, learned the hard way

- Every visual change gets checked at mobile width (~390px) and a normal desktop before publishing, and at ~2560px if the audience uses large screens.
- When adapting to large screens, scale whole modules together (type, dimensions, spacing, wraps). Scaling only headings leaves a small design floating in whitespace.
- Late CSS wins ties: media-query override blocks go at the end of the style block they override, or they silently lose the cascade. This has caused real bugs three times now (a mobile hero width, a mobile nav button that overflowed its menu, then the mobile nav *dropdown panels themselves* - `@media (max-width: 76rem) { .nav-dropdown-panel { visibility: visible; ... } }` sat before the unconditional base `.nav-dropdown-panel { visibility: hidden; }` in `site.css`, so the base rule always won and the mobile menu's dropdowns never actually opened, on any phone, until someone opened one and looked). That third case broke functionality, not just looks - a layout glitch is easy to spot scrolling past it, a menu that silently never opens is not, unless someone actually taps it. When adding *any* mobile/responsive override for a selector that already has an unconditional rule elsewhere, place the `@media` block immediately after that rule (not wherever feels natural in the file), and verify the computed style at the target width, not just that the code looks right.
  Verifying this one is itself tricky in this environment: reading `getComputedStyle` immediately (or even after a `setTimeout`) on a property that's mid-`transition` can report stale values when the Browser pane isn't actually displayed/compositing frames (a real, separate limitation seen throughout this project - screenshots fail with "the page is not compositing frames" when the pane is backgrounded). Don't conclude a transition-driven show/hide is broken from a hidden-tab computed-style read alone; either front the tab first, or test a state reached via `transition: none` (as the mobile nav override already sets) where the computed value can't lag behind the class change.
- Never put a standard CSS property and its `-webkit-`-prefixed twin (`backdrop-filter`, `mask-image`, etc.) as two declarations in the *same* rule - the production build's CSS minifier treats them as redundant duplicates and silently drops one (whichever came second in source), breaking whichever browser needed the dropped one. Put the `-webkit-` version in its own rule instead, guarded by `@supports not (<property>: <value>)`. This is a build-output bug, invisible in the dev server and in the source - the only way to catch it is to grep the actual files in `dist/` after `npx astro build`.
- Same "works in dev, breaks in the real build" trap for Node frontmatter code: don't resolve a filesystem path with `new URL('../relative/path', import.meta.url)` in a page's frontmatter - the production build bundles that file into `dist/.prerender/chunks/`, so the relative path resolves against the wrong location and throws `ENOENT` at build time even though `astro dev` never showed a problem. Use `path.join(process.cwd(), ...)` instead (stable in both modes, since `cwd` is always the `site/` root when running `astro dev`/`astro build` from there). Any page doing filesystem work (like the team gallery's `readdirSync`) needs an actual `npx astro build` run before shipping, not just a dev-server check.
- `.wrap`'s max-width/centering is defined as `.section-block .wrap` (site.css) - a descendant selector, not a standalone class. An element placed *between* two sections (not nested inside either one - e.g. a card straddling a section boundary with a negative margin) gets `class="wrap"` but silently stretches to the full viewport width, since the scoped rule never matches it. Give it its own explicit `max-width: var(--max-width); margin-left: auto; margin-right: auto;` (plus a `calc(100% - 2 * var(--space-4))` width so it still keeps edge padding below the max-width breakpoint) instead of assuming `.wrap` alone is enough.
- Adjacent `.section-block`s stack their padding-top + padding-bottom into a gap that reads as too big (default `--space-6` top and bottom = 16rem combined). Check every new section junction for this; the fix already used several times is `padding-bottom: var(--space-5)` on the section above and `padding-top: var(--space-5)` on the one below.
  This had only ever been fixed junction-by-junction as each one got touched for some other reason - by 2026-08-25 that left several *older* junctions still at the untouched default (`#projets` → `#equipe` and `#equipe` → `#soutenir` were both still 256px combined, worse than the ones already "fixed"). When the owner says spacing feels too big "in general" rather than pointing at one spot, measure every section's computed `padding-top`/`padding-bottom` on the live page and tighten every junction to the `space-5`/`space-5` standard in one pass, not just the one that prompted the complaint.
  Same over-stacking can happen *within* one section too, not just between two: the projects page's intro (kicker/h1/lede) → `.phases-image` → first `.section-sub` had two separate `margin-top: var(--space-5)` gaps back to back (one before the diagram, one after) - each looked fine alone but together, plus the diagram's own height, read as too much empty space before any project actually appeared. Tightened both to `var(--space-4)`. When several elements in a row each carry their own top margin, judge the *sum* against the page, not each margin in isolation.
  `.section-sub` is a page-scoped class redeclared separately in both `index.astro` and `innovations.astro` (Astro doesn't share page-scoped styles - see the component inventory note above). Tightening it in one page's `<style>` block does nothing for the other's identically-named copy: `innovations.astro`'s got fixed first, and `index.astro`'s sat at the untouched `var(--space-6)` default for a full extra session before the owner reported the same "too much blank space" complaint a third time and it turned out to be this. When a spacing fix applies to a class name that exists on more than one page, grep for every page-scoped redeclaration of it and check each one, not just the page you're currently looking at.
- A `vw`-based width tuned for desktop (to track some other element's own `vw` sizing) silently caps that same element at a fraction of the screen on mobile too, with no visual warning - it just quietly shrinks. Anything sized in `vw` needs an explicit check at ~375px, not just at desktop widths; the hero's text column once capped itself at 50vw on a phone (half the screen, for no reason - there was no second column to leave room for).
- No split screens or side-by-side columns on phones - single column, full width, always. When adding a new two-column layout, its mobile collapse is not optional and needs verifying at ~375px before publishing, not assumed from the desktop code.
- Body paragraphs justify, unconditionally, at every width (was mobile-only at first; corrected to apply everywhere) - but `hyphens: none`. `hyphens: auto` was tried to keep justified text from stretching, but it splits words mid-line, which reads worse than an early line wrap. Never re-enable it.
  That global `p { text-align: justify }` (site.css) is an element-type selector, so it silently wins over any component that only sets `text-align: center` on a *parent* wrapper and expects its `<p>` children to inherit it - inheritance always loses to an explicit rule, however low its specificity. The team member cards hit this: `.team-member-card { text-align: center }` had no effect on the name/role/credentials `<p>`s inside it, which rendered justified instead - on a card that narrow, justify turned 2-3-word lines into huge, uneven gaps and read as "broken." Fix: target the `<p>`s directly (`.team-member-card p { text-align: center }`), don't rely on inheritance from an ancestor when a bare-element global rule exists that could out-specificity it.
  Separately, `hyphens: none` only stops the browser from *inserting* hyphenation points - it does nothing to a word that already contains a literal hyphen (e.g. "Hépato-Biliaire"), which browsers can still break at when wrapping. In a narrow column that reads exactly like an inserted mid-word hyphenation break even though it isn't one. Fix per occurrence, not globally: swap the visible `-` for a non-breaking hyphen (U+2011) in that specific piece of copy, so the two halves stay on one line.
  This inherited-justify trap has now bitten three separate components (team cards, `.pipeline-step p` in "Le projet scientifique," and `.donate-text` - the last one introduced by a *later* session that added a new centered `<p>` without knowing to check for this). Whenever you add `text-align: center` to a container and it holds (or will hold) a bare `<p>`, add the `<container> p { text-align: center }` override in the same edit, proactively - don't wait for someone to notice the stretched text.
- The homepage's shared `main` gradient (see `site.css`) is a single white-to-cold-blue arc, only ever visible from the end of the hero's floating stat band through `#projets` (the hero itself, the stat band, and `#equipe`/`#soutenir` further down are all fully opaque, so whatever the gradient does behind them doesn't matter). Its stops are **fixed px, not %** - a % version was tried twice and broke twice: any edit that changed a section's height (trimmed copy, added/removed content) silently shifted which section landed on which color, once leaving the entire visible range washed-out white because `#equipe`'s start had drifted to 54% while the "fully blue" stop still targeted 80%. Fixed px doesn't drift with content-length changes above or below the gradient's own range.
  A second, subtler version of the same bug: even with fixed px, don't start the ramp's first color stop at `0px` if the top of `main` is covered by opaque content (the hero + its overlapping stat card, here) - that stretch of the ramp is spent somewhere invisible, so by the time content actually becomes visible the transition is already mostly "used up" and reads as a flat, colorless stripe rather than a perceptible gradient. Hold the starting color flat through the last opaque pixel (currently 664px) *before* the ramp begins, so the visible portion gets the ramp's full range. Re-anchor both this starting point and the endpoint (currently 3700px) if the hero/stat-band height or `#equipe`'s start position (currently ~3786px) move meaningfully - check with `document.querySelector('#equipe').getBoundingClientRect()`.
  A third version, found only once someone actually checked mobile: those anchors are desktop measurements and don't hold at narrow widths - the hero's text and the stat band both wrap onto more lines on a phone, so the opaque zone is taller (~1066px at 375px wide, not 664px) and every section stacking single-column instead of side-by-side pushes `#equipe`'s start much further down (~6098px, not ~3786px). Reusing the desktop anchors under `@media (max-width: 40rem)` left the ramp already partway into blue before any mobile content was visible - "gradient too dark" was the owner's framing of what was actually a miscalibrated start point. This gradient needs **two** sets of anchors, one per layout (see the `@media (max-width: 40rem)` override right after the base `main` rule), and both need re-measuring - independently - whenever section heights change on either breakpoint.
  Confirmed white-first and correct as of 2026-08-25 (`curl`/computed-style checked directly against the live production origin, not just the dev server) - if a future report says otherwise, verify the *live* site first (fetch its actual computed styles/asset bytes) before assuming the fix regressed. Twice now an owner report of "still broken" didn't match what was actually deployed; both times it was a stale browser/CDN cache on their end, not a real regression - point them at a hard refresh or a private window before re-diagnosing from scratch.
  `#equipe` is `.dark` now (navy team-card section, matching the owner's reference layout - was flat white for a while, see git history), with its own background gradient starting at `color-mix(in srgb, var(--bopa-blue-2) 35%, white)` - deliberately the same tone the shared gradient above reaches by its own endpoint, so the handoff between the two has no visible seam. If the shared gradient's endpoint color/position ever changes, update this starting color to match, or the seam comes back.
  A caveat to the "verify live, suspect caching" habit above: not every "still broken" report is caching. `#qui-sommes-nous` had carried `.fade-from-navy` (a navy-to-transparent top gradient, meant to blend from a dark section directly above) since before the hero stat band existed - once the white stat-band card was inserted between the hero and this section, the leftover fade kept painting a false navy smear right under the white card, reading as "white band with blue" (found and removed 2026-08-25). When a `fade-from-navy`/`fade-to-navy` class is on a section, check what's *actually* immediately adjacent to it now, not what used to be - inserting or removing a section/element next to one of these fades is exactly the kind of change that leaves it stale.
- Collapsed accordions (`<details>`) are for secondary/supplementary detail, not for a page's primary content - BOPtech's named projects (InMachina, Salle Hybride) were once the last thing on the page, hidden behind a click. Primary content goes early and stays visible by default.

## Accessibility baseline

- Text over background always passes contrast (4.5:1 for body text).
- Every meaningful image has real alt text.
- The site works with keyboard only; interactive elements are actual links and buttons.
